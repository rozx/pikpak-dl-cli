# ダウンロード、検証、再開

共有のダウンロード先のルートは、ローカルでのダウンロードを開始した時点で固定され、共有フォルダと名前の対応付けは永続化されます。既定のダウンロード先を変更すると、新しい共有と、ローカルにまだ何もない共有は新しいフォルダを使い、開始済みまたは完了済みの共有は元のフォルダのままです。新しい共有のタスクフォルダにはタスク名、つまり共有タイトルからファイルの拡張子を除いた名前を付けます（例：「Shibarin.7z.002」→「Shibarin」）。内部用の接尾辞は付けません。既存のフォルダと名前が重なる場合は「名前 (2)」とし、既存のフォルダには書き込みません。名前は、プラットフォームごとの予約語、使用できない文字、Unicode、大文字・小文字の衝突を考慮して処理します。同じ名前の新しいバージョンや、書き込み時に生じた保存先の衝突には安定した接尾辞を付け、既存のファイルを上書きしません。ダウンロード中の一時ファイルは「<ファイル名>.pikpak-part」として保存先の隣に置き、完了後にその場で名前を変更して書き込みを完了します。`.pikpak-staging` の一時フォルダは作成しなくなりました。

プログラムは元のバイナリのダウンロード URL だけを使い、メディアのトランスコード用 URL は使いません。既定では一度に一つのファイルだけをダウンロードします。8 MiB を超えるファイルは、既定で 4 本の HTTPS Range 接続を使い、固定 8 MiB のチャンクを並行してダウンロードします。各接続が受け持つのは、検証済みの先頭部分に続く限られた範囲内のチャンクだけです。接続数は `config --connections <1-8>` または全画面インターフェースの設定ページで変更でき、次のファイルから適用されます。1 にすると、初期のバージョンと同じく単一接続での順次ダウンロードになります。すべての接続は、確認済みの同じバージョンの署名付き URL を共有します。URL はメモリにだけ保持し、最長 30 秒経過したときか失効したときに一度だけ更新し、そのたびにコピーの ID、サイズ、GCID を改めて確認します。バージョンの変化を検知したら、すぐにすべての接続を止めます。

同時ダウンロード数は `config --files <1-5>` または設定ページで変更でき、既定は 1 です。実際に適用される値はアカウントの種類によっても制限されます。プログラムは会員情報を読み取り専用で照会し、会員は最大 5、無料アカウントや種類を一時的に読み取れない場合は 1 のみです。設定ページと `status` には、設定値、アカウントの種類、実際の値が並べて表示されます。スキャンとクラウドへの保存は常に一つずつ行います。各ファイルは保存の前に枠を一つ確保し、ダウンロード、検証、書き込みが完了した時点（または失敗、キャンセル、中断した時点）で解放します。そのため、クラウドにある未引き渡しのコピーの数は枠の数を超えず、ダウンロード中のコピーが回収されることはありません。処理中の各ファイルはそれぞれ接続数の設定（最大 8）を使い、同時ダウンロード数によって減ることはありません。あるファイルがレート制限を受けた場合は、そのファイル自身の接続数だけを下げます。ファイルをキャンセルしても止まるのはそのファイルだけです。キューの一時停止、プログラムの終了、あるいはアカウント単位の一時停止（ログインの期限切れ、転送量不足、レート制限、ローカルディスクの容量不足など）では、処理中のすべてのファイルが安全な位置で停止し、チェックポイントを保存します。

一部の接続がレート制限（429）を受けた場合は、まずそのファイルの並列数を半分にし、サーバーの待機指示に従って間を空けます。成功が続けば徐々に元に戻します。単一接続まで下げてもまだ制限される場合や、待機が 60 秒を超える場合に初めて、アカウントのレート制限として一時停止します。転送量の不足（402）ではすぐに停止します。一本の接続が切断または停滞した場合、そのチャンクは受信済みの位置からほかの接続が引き継ぎます。同じチャンクが 3 回続けて失敗した場合、またはファイル全体で 6 回続けて失敗しその間に完了したチャンクがない場合に限り、ファイル単位の回数制限付き再試行に数えます。サーバーが範囲指定を無視した場合、`Content-Range` が一致しない場合、応答が範囲を超えた場合は、そのデータを追記しません。そのファイルは単一接続の順次モードに切り替えて最初からダウンロードし、その後も同じことが起きれば範囲の不一致として報告します。明示的な `retry` は順次モードを解除し、自動の再試行では維持します。誤った範囲、途中で切れた内容、バージョンの変化、ダイジェストの不一致は、いずれも完了の記録にはなりません。

一時ファイルはタスクのバージョンに結び付いています。チェックポイントは、連続した検証済みの先頭部分（オフセットと先頭部分の SHA-256）と、その後に続く最大 16 個のチャンク区間（それぞれの開始位置、書き込み済みバイト数、SHA-256）で構成されます。保存時はまず `sync` し、次に完了した先頭側のチャンクをディスクから読み戻して受信時のダイジェストと照合したうえで先頭部分に組み込み、最後に一回の書き込みで保存します。そのため、クラッシュしてもチェックポイントがディスクに書かれていないバイトを含むことはありません。再開時は先頭部分を読み直して確認し、一致しなければ最初からやり直します。先頭部分が有効であれば区間を一つずつ読み戻し、一致しない区間だけを破棄します。画面に前回表示された進捗は信用しません。切り捨てるのはファイルサイズを超えた部分だけで、先頭部分以降の確認済みの区間は残します。GCID は従来どおりのアルゴリズムで順に計算し、入力にはチャンクごとに確認したディスク上のデータを使います。完了後にサーバーの値と照合し、ファイル全体を読み戻して検証するとともに、ローカルの SHA-256 も保存します。ただし、ローカルの SHA-256 があっても、サーバーが同じアルゴリズムのダイジェストを提供しているわけではありません。

正式な書き込みの前に、保存先、試行番号、一時ファイルの ID、完全なダイジェストを保存します。衝突によってパスを変えるときは、そのたびにまず新しい意図を記録します。すべてのプラットフォームで、ディレクトリハンドルを基準にした相対パスで操作し、上書きしない方法で名前を変更します。macOS ではネイティブモジュール、Windows では常駐する PowerShell ブリッジ（データの読み書きはファイルディスクリプター経由）を使い、Linux では libc 経由で `openat` と `renameat2(RENAME_NOREPLACE)` を呼び出します。再開時の確認では、最後に保存したパス、ボリュームとファイルの ID、完全なダイジェストを照合します。ユーザーの既存ファイルの内容が同じというだけで、書き込みに成功したと見なすことはありません。

保存済みのコピーがある場合、再開時はアカウント内の正確な ID での読み取りを優先し、元の共有に引き続きアクセスできることを改めて求めません。同じ元のバージョンを限られた回数の範囲で保存し直せるのは、ファイルが存在しないことを示す明確な分類の場合だけです。通常の 404、権限の失敗、ネットワークエラーは、コピーが失われた証拠にはなりません。一意に確認できない書き込みや書き込み完了処理は記録を残して確認を待ち、そのまま再送信したり削除の範囲を広げたりはしません。

一時ファイルやフォルダが置き換えられた場合は、既存のリソースを残します。保護を回避するためにタスクデータベースを直接編集しないでください。キャンセルはスケジュールを止めるだけで、すでに行われた引き渡しを取り消すことはなく、未引き渡しのコピーに削除の資格を与えることもありません。
