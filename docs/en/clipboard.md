# Copying share text

Copy the complete text in one go, so that the link and the pass code are in the same snapshot. The example below only shows a synthetic format and points to no real resource:

```text
Link: https://mypikpak.com/s/synthetic-one
Password: demo
```

The pass code can be labelled the way any PikPak client labels it in its own language, or with a common synonym: `Password`, `Pass code`, `Access code`, `提取码`, `密码`, `识别码`, `パスワード`, `パスコード`, `비밀번호`, `Kata sandi`, `Kata laluan`, `Contraseña`, `Senha`, `Пароль`, `كلمة المرور` and more. In English and other languages that separate words with spaces, put a colon, an equals sign or `is` between the label and the code (`Password: demo`, `the password is demo`). The code may be wrapped in brackets or quotes, or sit alone on the next line after a trailing colon, as long as that line is the last one or is followed by a blank line (otherwise it may be a file name from a template and is not taken as the pass code). Archive (unzip) passwords, account or sign-in passwords, Vault share keys and Wi-Fi passwords are never taken as the pass code. A label with nothing after it on the same line counts as no pass code; this is what the PikPak web client produces in Japanese (`パスワード:` is left empty), so add the code and copy or paste the text again.

Without any label, only one shape is recognized: the whole text is one line with the link and one line with the pass code alone (blank lines in between are fine). Any other unlabelled text is never taken as the pass code.

Explicitly labelled `pwd`, `password`, `passcode` or `pass_code` parameters in the link are also supported, and for a share without a pass code you can copy just the link. A missing pass code and a wrong pass code have been observed as `PASS_CODE_EMPTY` and `PASS_CODE_ERROR`. Neither is treated as the whole account failing. The share row turns red and reads “The share needs a pass code” or “Wrong pass code”: select the share and press Enter to type the pass code and scan again, or copy the complete text again. A pass code copied on its own later is never paired with a waiting share automatically.

Several shares can each take their own line or paragraph, as long as each pass code is clearly paired. A pass code after several links that cannot be told apart is never guessed; copy them separately. Look-alike domains, other PikPak pages, a pass code on its own and ordinary text do not create tasks. The raw clipboard is never written to logs or the database.

Only a receipt with a task ID means the details and the request were saved. If some shares in one copy fail to save, the confirmed shares are kept and watching retries only the unconfirmed part. The clipboard is a snapshot of its current content: copying quickly can overwrite content that has not been read yet, and the change counter cannot restore history. If you see no receipt, copy again.

Copying the same text again can trigger an incremental scan. Leaving the clipboard unchanged does not keep scanning, and remote shares are not checked for updates on a timer. A completed version that has not changed is not downloaded again automatically, even if you moved its local files away; a new version with the same name keeps the old files. After the failure budget runs out, stop watching and run `retry <task ID>` to start a new limited retry cycle. Copying the share does not reset a file's retry budget.

When you change the default folder, new shares and shares with nothing local yet use the new folder. Later files of shares that have started downloading or are completed keep using their original folder. `cancel` keeps the resources and a cancel mark; copying the same share again does not restart a cancelled share. In the interface, press `x` to delete a cancelled task; see [Cloud space](cloud-space.md).

In the full-screen interface, clipboard watching is on by default and can be turned off in Settings; when off, press `a` to paste share text. The paste box uses the same parsing rules as the clipboard. Clipboard reading is isolated in a child process, so a failure does not block downloads. macOS reads a snapshot of the system clipboard, Windows reads it through the system PowerShell, and Linux calls `wl-paste` (Wayland) or `xclip` / `xsel` (X11). Without a usable clipboard, the interface shows a watching error, and pasting still works.

Each time watching starts (when the program starts, or when you turn watching back on in Settings), the text already on the clipboard only serves as the starting point and is not picked up. Later copies are picked up, even if the text is the same. To pick up something copied before the start, copy it again or press `a` to paste it. Linux has no system-wide copy events, so only a change in the clipboard text counts as a new copy: copying text identical to what is already on the clipboard, including the text present at startup, is not picked up. In that case, copy any other text first and then copy the share text again; in the full-screen interface you can also press `a` to paste it.

When the full-screen interface receives a share from the clipboard, the event area says it came from the clipboard, and the program tries to bring the terminal window to the front: on Windows it activates the Windows Terminal or console window (hosts without a visible window, such as editor-integrated terminals, are skipped); on macOS it activates the terminal app that started the program; on Linux X11 it activates the terminal window when `xdotool` is installed. On Wayland only the event area shows it. Manual pasting and `watch` do not switch windows.
