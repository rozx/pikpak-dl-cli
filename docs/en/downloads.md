# Downloading, verification and recovery

The download root is fixed when a share starts downloading locally, and the share's folder and name mapping are stored. When you change the default folder, new shares and shares with nothing local yet use the new folder; shares already started or completed keep their original folder. A new share's task folder is named after the task name, which is the share title without its file extension (for example "Shibarin.7z.002" → "Shibarin"), with no internal suffix. If a folder with that name already exists, it uses "Name (2)" instead of writing into the existing folder. Names are adjusted for reserved words on each platform, illegal characters, Unicode and case conflicts. A new version with the same name, or a target conflict found at publish time, gets a stable suffix; existing files are never overwritten. While downloading, the temporary file is kept next to the target as "<file name>.pikpak-part" and is renamed in place when done. No `.pikpak-staging` folder is created anymore.

The program uses only the original binary download URL, never a media transcoding URL. By default, one file downloads at a time. Files larger than 8 MiB download by default over 4 HTTPS Range connections in parallel, in fixed 8 MiB chunks; a connection only takes chunks within a limited window after the verified prefix. Change the number of connections with `config --connections <1-8>` or in the full-screen interface's Settings; it takes effect from the next file. With 1, it downloads sequentially over one connection, as early versions did. All connections share the same signed URL for the verified version. The URL is kept only in memory and refreshed once after at most 30 seconds or when it expires, at which point the copy's identity, size and GCID are checked again. If the version has changed, all connections stop at once.

Change the number of files downloading at once with `config --files <1-5>` or in Settings; the default is 1. The effective value is also limited by the account tier. The program reads the membership details read-only: members get up to 5, while free accounts, or accounts whose tier cannot be read for now, get only 1. Settings and `status` show the configured value, the tier and the effective value together. Scanning and saving to the cloud always happen one file at a time. Each file takes a slot before it is saved, and frees it only after downloading, verification and publishing finish (or fail, are cancelled or interrupted). So the cloud never holds more undelivered copies than there are slots, and a copy being downloaded is never reclaimed. Each file in progress uses the full connection setting (up to 8), regardless of how many files download at once. When one file is rate limited, only its own connections are reduced. Cancelling a file stops only that file. Pausing the queue, quitting the program, or any account-level pause (expired sign-in, traffic quota used up, rate limiting, a full local disk and so on) stops all files in progress at a safe point and saves their progress.

When some connections are rate limited (429), the file's parallelism is first halved and it cools down as the server's wait hint says; after sustained success it recovers step by step. Only when it is still rate limited after dropping to a single connection, or the wait exceeds 60 seconds, does it pause as account rate limiting. An exhausted traffic quota (402) stops immediately. When a single connection drops or stalls, other connections continue that chunk from where it got to. It counts toward the file-level limited retries only after the same chunk fails 3 times in a row, or the whole file fails 6 times in a row with no chunk completed in between. If the server ignores the range, `Content-Range` does not match, or the response goes beyond the range, that data is not appended: the file switches to sequential mode over one connection and starts over, and if it happens again, a range mismatch is reported. An explicit `retry` clears sequential mode; automatic retries keep it. A wrong range, truncation, a version change or a digest mismatch can never become a completion record.

The temporary file is bound to the task version. The checkpoint holds the contiguous verified prefix (offset and prefix SHA-256) and at most 16 chunk ranges after the prefix (each with its start, bytes written and SHA-256). When saving, the program first runs `sync`, then reads completed leading chunks back from disk, compares them with the digests taken when they were received and merges them into the prefix, and finally saves everything in one write. After a crash, the checkpoint never claims bytes that were not on disk. On resume, the prefix is read again and checked; if it does not match, the download starts over. If the prefix is valid, each range is read back and only ranges that do not match are dropped; the progress the UI showed last is not trusted. Only the part beyond the file size is truncated, and verified ranges after the prefix are kept. The GCID is still computed sequentially with the original algorithm, from disk data verified chunk by chunk. When done, it is compared with the server's value and the whole file is read back to check it, and the local SHA-256 is saved as well. A local SHA-256 does not mean the server provided a digest with the same algorithm.

Before the final publish, the target, attempt number, staged file identity and full digest are saved. Every time a conflict changes the path, a new intent is committed first. All platforms use relative path operations based on directory handles and rename without overwriting: macOS uses a native module, Windows uses a resident PowerShell bridge (data reads and writes go through file descriptors), and Linux calls `openat` and `renameat2(RENAME_NOREPLACE)` through libc. Recovery checks the last saved path, the volume and file identity and the full digest. It never claims success just because a file you already had has the same content.

When a saved copy already exists, recovery first reads it by its exact ID in the account and does not require the original share to still be accessible. Only an explicit "file does not exist" category allows saving the same source version again, within a limited budget. A plain 404, a permission failure or a network error does not prove that the copy is lost. A write or publish that cannot be confirmed uniquely keeps its record and waits to be checked; it is never resent directly, and the delete scope is never widened.

If the temporary file or folder is replaced, the existing resources are kept. Do not edit the task database directly to get around these protections. Cancelling stops scheduling; it does not undo deliveries that already happened, and it does not make undelivered copies eligible for cleanup.
