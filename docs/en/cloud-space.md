# Cloud space and reclaiming

The cloud drive is only a staging area. Permanently deleting completed copies is considered only when the next file does not fit; nothing is cleared early while there is enough cloud space. The program first checks the local target and the remaining download bytes it can verify, then validates the share and the source version, and only then plans cloud capacity.

A candidate must meet all of these: it belongs to the current account; this tool holds clear proof of creating it; the local content is verified and published; every reference to it has been delivered; and its current remote identity, version, name and parent folder still match the record. The proof consists of the separate save task returned for this request, an exact source mapping, the original share and source file IDs, the creation timing and the content fingerprint. A name, time or size alone is never enough to claim ownership.

Candidates are processed from oldest to newest by the local completion time of their last reference; ties are ordered by remote ID. The program first makes sure the valid candidates add up to enough space. Then, one at a time, it checks each again, records the delete intent and submits only the exact ID. After each deletion it checks the result and the actual capacity, and stops as soon as the next file fits. The trash is never emptied, and folders are never deleted recursively.

Completed local files are yours to manage. Moving, changing or deleting a local file later does not revoke its cloud copy's earlier eligibility for reclaiming. Copies are never reclaimed automatically if they are unfinished, failed, cancelled before delivery, of unclear ownership, renamed, moved or changed in content, or still have unfinished references.

If the cloud drive is already full on first use, or holds only failed copies so that nothing can be reclaimed safely, the file waits for space; other, smaller files can continue. A single file larger than the account's total capacity fails clearly, and nothing is deleted for it in vain.

If a delete response is lost, the same object is checked again; no other resource is deleted instead. If automatic reclaiming is refused for lack of permission, execution pauses. If the capacity is slow to update, the program waits a limited time and then shows that it is waiting for sync; a successful request is not taken to mean that all the space was freed at once. Traffic quotas, rate limiting, authentication failures and local disk problems never trigger cloud reclaiming.

## Releasing manually

In the interface, select a file or share and press `x` to release its cloud copies right away, without waiting for the next file to need space. Press `X` to release the cloud copies of all completed and cancelled tasks; tasks still in progress are not affected. A file being released shows "Releasing". Some eligibility rules are the same as for automatic reclaiming: only copies that this tool created, has proof of ownership for and still keeps are handled, and their remote identity, name, parent folder and content fingerprint are checked again before deletion. The difference is that the file does not have to be completed (it can be queued, paused, cancelled, failed or waiting). Files being downloaded, verified or written to disk, files with an unverified save, and copies not created by this tool are not released; the interface only explains why.

The confirmation dialog says that deletion is permanent (nothing goes to the trash) and that local files are kept. Once the copy of a completed file is released, that task's record is deleted too and it disappears from the list. A completed task whose copy is already gone from the cloud (for example, reclaimed automatically earlier) can also be removed with `x`, which deletes only the record. When all file records of a share are deleted, the share record and its pass code are deleted as well; copying the same share again later downloads it as a new task. When the copy of an unfinished file is released, the file goes back to queued and keeps its progress. On resuming, it is saved from the share again through the normal flow and then continues from its saved progress. If the share has expired, the file cannot be completed and new share details are needed.

Cancelled tasks are handled like completed ones: their records are deleted once their copies are released, and if no copy is left in the cloud, only the record is deleted. Before deleting the record of a cancelled file, its unfinished temporary file (`.pikpak-part`) is checked against the recorded identity and deleted. If it is already gone, it counts as deleted; if the identity does not match or its disk is unavailable, the record is kept and the event area explains why. A share that was cancelled after its scan failed and has no files can also be deleted with `x`.

Manual releasing and automatic reclaiming share one cloud operation lock, so they never send deletes for the same copy at the same time. When several copies are released at once, they are first checked in parallel (at most 4 requests at a time), then deleted with one request per batch of at most 100 IDs. Once a delete is accepted, it is confirmed by the copy no longer being visible, without waiting for the cloud quota to update; copies that are still visible are checked again for up to 30 seconds. Delete requests are sent in silent mode. If the server clearly refuses (a 4xx other than 401, for example when the authorization lacks permanent delete permission), the copy goes back to kept, the delete intent is recorded as refused, the event area shows the reason, and the account is not paused. Other outcomes, such as an expired sign-in or a lost network connection, follow the rules above and are checked at the next startup. After a successful release, the event area reports the space freed and the cloud quota is refreshed.

The batching loop and the failure paths above are covered by tests against a synthetic service. Release and Release all have been tested on Windows with a real account, where the server allowed permanent deletion.
