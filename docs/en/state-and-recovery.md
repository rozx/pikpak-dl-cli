# Local state and recovery

The default state directory is `~/Library/Application Support/PikpakDownloader` on macOS, `%LOCALAPPDATA%\PikpakDownloader` on Windows, or `$XDG_DATA_HOME/PikpakDownloader` on Linux (`~/.local/share/PikpakDownloader` when unset). `PIKPAK_DOWNLOADER_STATE_DIR` can point to another directory for local testing; one task database path must have only one writing instance. The credentials belong to this app under the current system user, so in the first version, do not run several executors with different state directories at the same time. Downloaded files go into the output folder fixed when the share was received; the task database does not move with the download folder.

`tasks.sqlite` stores the account ID, references to access details, the fixed output root, scan generations, file versions, save/delete/publish intents and delivery records. Passwords, tokens, pass codes, the raw clipboard and signed URLs never enter the task database. The credentials are held by the system's protected storage; a database backup alone cannot replace a credential backup or authorizing again.

The schema version uses SQLite `user_version`, plus a check of the application ID. The program refuses to write to a newer schema or to another application's database. The current version is 5, which includes scan progress, folder identity, publish path mapping, segmented download checkpoints and pause marks. Migration from development versions 1–4 is supported. Migration runs while holding the write lock with execution stopped: it first creates a consistent backup with a recovery-review mark, then upgrades in a transaction. There is no automatic downgrade.

The backup feature creates a private, consistent snapshot marked `backup_review_required` and never overwrites an existing file. You can inspect an old-schema snapshot with a read-only SQLite tool, but it cannot run directly as the active queue; status queries in the current CLI use the current schema. An old backup may miss saves, publishes or permanent deletions that happened later. Before recovery, the unknown remote operations, local file identities and deliveries that already happened must be checked, and then a controlled recovery process enables writing. The first version has no command that restores an old backup and continues right away.

After the task database is lost, files with the same name or content in the cloud, or existing folders, cannot automatically become owned by this tool. Reinstalling never takes them over or deletes them based on their names. Local completion history cannot be rebuilt just by scanning folders either; this tool is not a backup repair or folder sync tool.

SQLite uses WAL, `synchronous=FULL`, foreign keys and short synchronous transactions. Network and credential operations cannot go inside a transaction callback. Data sizes are stored as decimal strings and converted to `bigint`; request versions and retry counts use exact integers.

Mutual exclusion while running uses a separate `queue-lock.sqlite`. The instance holds the system file lock used by its EXCLUSIVE transaction, and the system releases it when the instance exits or crashes. Whether the lock is taken is never judged by whether a file exists, and no long transaction is held on the task database, so `status` can still query an active queue read-only. Tests cover cross-process locking, write conflicts and taking the lock again after a forced exit on macOS, Windows and Linux.
